# dev 压力合格率根因分析 (真实历史代理需求驱动)

> 需求口径: `demand = 真实 SCADA 站级总供气量` (5min 均值) 作为**历史代理需求**;
> 非独立实测用户侧需求。压力为工程一阶模型 (K_VOL=23700 等, 校验见 energy/pressure JSON)。
> 合格带 CAL-05 示例 [0.55, 0.66] MPa; 容量 = 2×268.9 = 537.8 m³/min。

## 0. 重要更正: 71.45% 是**截断前缀**的结果
- 先前 `pressure_real_dev.json` 使用 `--max-steps 20000` (dev 前 20000 步 ≈ 前 69 天),
  得到 joint 合格率 **71.45%**。
- **full dev (40609 步, 3/12–7/31)** joint 合格率 = **85.92%**。
- 关键: **全部 5321 个超容量步都集中在前 20000 步内**; 后 ~20609 步超容量步 = **0**,
  且后段仅新增 7 个不合格步 (容量可行不合格 1068→1075)。
- 即: dev 的容量受限期集中在前 69 天; 其余时段 joint 合格率 ≈ 99.97%。

## 2. 超容量步 (dev full)
- 超容量步: **5321** (13.1%); 连续超容量段 **112** 段;
- 最长单段 **741 步 = 3705 min = 61.7 h**; 超额流量 ∫ = **489,228 m³**;
- 全部集中在前 69 天 (前 20000 步占比 26.6%)。

## 3. 不合格 ∩ 超容量
- 超容量且不合格: **4642** 步 = 不合格的 **81.2%**。

## 4. 超容量结束后的恢复滞后
- 超容量段结束后仍未回到带内的步: **391** 步 (分类口径, 最长回带 24 步=2h)。

## 5. 容量充足但不合格
- 容量可行 (demand ≤ 537.8) 但不合格: **1075** 步 = 不合格的 **18.8%**;
  其中 recovery 391 (6.8%) + **steady_control 684 (12.0%)**。

## 6. 逐步原因分类 (dev full, 不合格 5717)
| 类别 | 步数 | 占不合格 |

## 7. 物理可行工况合格率
| 范围 | 步数 | joint 合格率 |
|---|---|---|
| 容量可行步 (demand ≤ 537.8) | 35288 | **96.95%** |

> 结论: 在**物理可行连续工况**下 joint 达 99.03% (接近但未达 99.5%); 未达标主要由
> 容量不足 (13.1% 步) 及其恢复滞后造成, 不能通过删除超容量步宣布达标。

## 9. 结论 (直接回答)
- **dev 不合格主因: 容量不足** (81.2% 直接 + 6.8% 恢复滞后 = 88.0%)。
- 控制可改善空间: **684 步 = 12.0% 的不合格** (在容量充足时仍掉压), 但仅占全部步 1.7%。
- 物理可行连续工况下 joint 合格率 **99.03%**, 已接近 99.5% 目标; 剩余差距(≈0.5pp)来自稳态控制与恢复过程。
- 71.45% 系**截断前缀**口径; full dev 应为 **85.92%**。
