# RUL 智能体能力——四人并行开发与集成方案

## 1. 文档目的

本文说明在现有空压站多机协同智能调度系统中，如何由 A、B、C、D 四名成员并行增加 RUL（Remaining Useful Life，剩余使用寿命）能力，并将它接入健康诊断、调度优化、MCP 服务和前端演示。

这里的 **RUL 不是 URL**：

- RUL：设备距离预期失效还剩多少小时；
- URL：网页或接口地址，与本任务无关。

RUL 是健康管理能力的增强项，不应替代当前已经冻结的 `health_json()` 健康诊断接口，也不应被描述为已经基于真实故障数据验证的寿命预测。

---

## 2. 为什么前面的方案没有安排 RUL

前面的 A 模块优先完成了赛题基础闭环需要的内容：数据治理、负荷预测和设备健康诊断。RUL 当时没有列为必做内容，主要有以下原因：

1. **赛题硬性接口要求是健康诊断，不是必须单独提供 RUL 模型。** 当前 `health_json()` 已经能输出健康分、风险等级、异常因素、趋势和维护建议。
2. **现有真实数据没有可靠的“失效时刻”标签。** 只有故障码、保养记录和运行计数，无法直接计算真实剩余寿命。
3. **维护剩余时间不等于 RUL。** `maintenance_remaining_hours` 表示距离计划保养还有多久，不能改名后当成设备真实寿命。
4. **故障码 26 是弱标签，而且两台设备同步出现。** 它更像站级共同事件，不能直接作为单台设备寿命终点。
5. **先完成可验证的基础能力风险更低。** 在数据依据不足时直接宣称真实 RUL 准确率，会影响答辩可信度。

因此，现在增加 RUL 的正确定位是：

> 使用可复现的模拟退化数据训练和验证 RUL 模型，为多智能体调度演示提供寿命风险信息；所有输出明确标记 `validation_mode: simulation`，不宣称是真实设备寿命结论。

---

## 3. RUL 在多智能体系统中的位置

RUL 不是一个独立下控制命令的智能体，而是健康智能体提供的一项预测能力。其协作关系如下：

```text
设备实时/历史数据
        ↓
健康智能体（健康分、异常、趋势、RUL）
        ↓
调度智能体（把 RUL 作为软约束或惩罚项）
        ↓
安全校验与控制智能体（校验后才允许形成控制建议）
        ↓
前端展示与人工确认
```

各能力的边界：

- 健康智能体负责判断风险和估计 RUL，不直接启停设备；
- 调度智能体使用 RUL 调整机组优先级，但不能只凭 RUL 强制停机；
- 控制智能体仍需检查压力、喘振、启停频率和设备可用性等安全约束；
- 前端明确展示“模拟验证”和预测区间，避免把估计值显示成确定结论。

---

## 4. 总体并行流程

```text
A 先提交 RUL 接口文档和样例 JSON
                    ↓
        A、B、C、D 同时开发
        ├─ A：模拟数据、RUL 模型、评估和 rul_json()
        ├─ B：调度模型中的 RUL 软约束与降级策略
        ├─ C：RUL MCP/API、错误处理和智能体工作流
        └─ D：RUL 页面、图表、告警和演示场景
                    ↓
A 提交 RUL 模型、指标、报告和自动化测试
                    ↓
C 将样例 fixture 替换为真实 rul_json()
                    ↓
B 用真实输出接入 RUL 软约束
                    ↓
D 将页面切换到 C 提供的真实 API
                    ↓
四人联合测试多智能体完整链路
```

可以并行的关键原因是：A 先冻结数据契约。B、C、D 不需要等待模型训练完成，只需根据固定 JSON 样例开发。后续只替换数据来源，不修改字段和业务语义。

## 5. 第一步：A 冻结 RUL 接口

### 5.1 A 必须先提交的内容

A 在开始模型开发前先提交以下文件：

```text
analysis/reports/A_to_B_RUL接口.md
analysis/reports/A_to_C_RUL服务接口.md
data/fixtures/rul_success.json
data/fixtures/rul_error.json
```

文档需写清：

- RUL 的业务定义和单位；
- 输入数据、输出字段和字段类型；
- `simulation` 的验证含义；
- 调度允许怎样使用 RUL；
- 哪些情况只能告警、不能自动停机；
- 文件、配置和模型缺失时的异常行为；
- 维护剩余时间和 RUL 的区别。

### 5.2 唯一运行时函数

新增独立入口：

```python
from air_station.models.rul.service import rul_json

result = rul_json()
```

不得修改现有两个冻结接口：

```python
forecast_json()
health_json()
```

这样可以避免 RUL 开发破坏 B、C 已经接入的预测和健康功能。


### 5.4 接口冻结规则

- 函数名固定为 `rul_json()`；
- MCP 工具名固定为 `rul_estimation`；
- RUL 单位固定为小时；
- `evaluation_time` 使用 UTC ISO 8601，并以 `Z` 结尾；
- `device_id` 使用 `4#`、`5#`；
- `validation_mode` 当前必须是 `simulation`；
- `lower_bound_hours <= estimated_rul_hours <= upper_bound_hours`；
- 所有数值必须有限且非负；
- 设备顺序固定为 `4#`、`5#`；
- 失败时不返回伪造的 `status: success`；
- 若以后获得真实失效标签，可新增验证模式，但不得悄悄把 `simulation` 改成真实验证。

### 5.5 第一步验收标准

- B、C、D 对所有字段名称和含义确认无异议；
- 样例 JSON 能通过严格 JSON 解析；
- 样例中无 `NaN`、`Infinity` 和缺失必填字段；
- B、C、D 能仅凭文档和 fixture 开始开发；
- 这一步只冻结接口，不要求模型已经完成。

## 6. 第二步：四人同时开发

## 6.1 A：RUL 数据、模型、评估与服务

### 任务

1. 根据真实设备数据范围设计模拟退化过程；
2. 模拟正常、缓慢退化、快速退化、维护复位和噪声干扰场景；
3. 生成带 `episode_id`、时间、设备特征和真实模拟 RUL 标签的数据；
4. 建立简单趋势外推基线；
5. 建立回归模型并输出预测区间；
6. 评估模型并生成报告；
7. 实现 `rul_json()`；
8. 编写接口和模型自动化测试。

### 建议算法

- 基线：健康分或退化指标线性趋势外推到阈值；
- 主模型：`GradientBoostingRegressor`；
- 中位预测：普通回归或分位数 0.5；
- 下界模型：分位数 0.1；
- 上界模型：分位数 0.9。

当前数据量和演示目标不需要深度学习。可解释、可复现、依赖少的模型更适合比赛原型。

### 数据要求

- 每条模拟序列有唯一 `episode_id`；
- 训练、验证、测试按 `episode_id` 划分，禁止同一退化序列跨集合；
- 所有模拟记录标记 `origin: simulated`；
- 固定随机种子，保证重复运行得到一致结果；
- RUL 在无维护的退化过程中总体下降；
- 维护完成后允许退化状态复位并开始新 episode；
- 特征范围应参考真实 4#/5# 数据，不能生成明显脱离业务的数据。

### A 的产物

```text
configs/rul.yaml
data/simulated/rul_sequences.parquet
src/air_station/models/rul/__init__.py
src/air_station/models/rul/simulator.py
src/air_station/models/rul/features.py
src/air_station/models/rul/baselines.py
src/air_station/models/rul/train.py
src/air_station/models/rul/evaluate.py
src/air_station/models/rul/service.py
tests/models/test_rul.py
artifacts/models/rul_median.pkl
artifacts/models/rul_lower.pkl
artifacts/models/rul_upper.pkl
artifacts/metrics/rul_metrics.json
analysis/reports/phaseA5_rul/rul_report.md
```

### A 的验收指标

- 数据可由固定种子重复生成；
- 划分不存在 episode 泄漏；
- 主模型测试集 MAE、RMSE、MAPE 均有记录；
- 记录预测落在真实值 ±20% 的比例；
- 记录预测区间覆盖率；
- 记录预测随退化过程总体下降的单调性指标；
- 主模型至少优于简单趋势基线中的一个核心指标；
- `rul_json()` 输出严格符合冻结结构；
- 所有数值有限、非负且区间顺序正确；
- 报告明确声明使用模拟数据，不写成真实寿命精度。

## 6.2 B：RUL 调度软约束

### 任务

1. 从 `data/fixtures/rul_success.json` 读取 RUL；
2. 将 RUL 转换为调度惩罚，不设置为唯一硬停机条件；
3. 让短 RUL、低置信度或加速退化设备降低加载优先级；
4. 保证总供气、母管压力、喘振边界等现有硬约束优先；
5. 在 RUL 服务不可用时退化到现有 `health_json()` 风险等级；
6. 输出调度前后设备负载和采用 RUL 的解释。

### 推荐软约束逻辑

可以先使用可配置分段规则：

| 条件 | 调度处理 |
|---|---|
| RUL > 500 h | 不增加惩罚 |
| 200 h < RUL ≤ 500 h | 小幅降低优先级 |
| 72 h < RUL ≤ 200 h | 明显降载，优先使用其他健康机组 |
| RUL ≤ 72 h | 强惩罚并触发人工确认，但不单独作为自动停机命令 |
| confidence = low | 降低 RUL 约束权重，避免过度相信模型 |
| RUL 服务失败 | 使用健康风险等级继续调度并记录降级原因 |

具体阈值应写入配置，不能硬编码在算法中。上述值只作为第一版演示参数，并非真实工业维护标准。

### B 的产物

- RUL 软约束配置；
- RUL 惩罚函数；
- 调度目标函数接入代码；
- 服务正常、低 RUL、服务失败三类测试；
- 调度解释结果；
- 接入前后能耗、压力、负载分配和风险指标对比。

### B 的验收标准

- RUL 较短的设备在同等条件下加载优先级下降；
- 不因 RUL 软约束破坏压力和供气硬约束；
- 不因单一模拟 RUL 结果直接产生强制停机命令；
- RUL 服务不可用时调度仍可运行；
- 调度结果能解释“哪台设备为什么被降载”；
- 调度函数可先用 fixture 测试，之后替换真实接口无需改字段。

## 6.3 C：RUL MCP/API 与智能体工作流

### 任务

1. 先使用 fixture 实现 `rul_estimation` MCP 工具；
2. 同时提供前端可调用的 REST API；
3. 定义统一成功和失败响应；
4. 将 RUL 能力注册到健康智能体工具列表；
5. 在调度请求需要寿命信息时调用 RUL 服务；
6. 记录调用时间、成功状态、模型验证模式和错误原因；
7. A 完成模型后，将 fixture 数据源替换为 `rul_json()`。

### 建议接口

```text
MCP tool: rul_estimation
REST API: GET /api/v1/health/rul
```

### 调用边界

- C 只调用 `rul_json()`，不复制 A 的训练或特征代码；
- 不修改 A 返回的成功字段名称；
- 可在服务层包裹统一的 HTTP/MCP 错误结构；
- 模型或数据缺失时返回明确错误，不能返回模拟的成功值；
- 接口超时或失败时通知调度工作流走降级路径；
- RUL 结果仅作为健康和调度依据，不直接调用 PLC。

### C 的产物

- `rul_estimation` MCP 工具；
- RUL REST API；
- fixture 适配器与真实 `rul_json()` 适配器；
- JSON 校验模型；
- 错误码和日志；
- MCP/API 单元测试与集成测试；
- 健康智能体和调度智能体调用 RUL 的工作流节点。

### C 的验收标准

- fixture 阶段即可返回冻结 JSON；
- 替换为 `rul_json()` 后接口地址和响应结构不变；
- 正常调用、文件缺失、模型缺失、输出非法和超时均有测试；
- `validation_mode` 和免责声明原样传递；
- API 输出可被严格 JSON 序列化；
- 失败时返回失败状态，不伪造预测结果；
- P95 服务响应时间应记录，比赛演示环境建议小于 2 秒。

## 6.4 D：RUL 页面与演示场景

### 任务

1. 使用 fixture 开发 RUL 展示卡片和趋势图；
2. 展示估计值、上下界、置信度、退化阶段和限制因素；
3. 明确显示“模拟数据验证”标签和免责声明；
4. 建立低 RUL 告警和人工确认交互；
5. 展示 RUL 如何影响调度优先级和负载分配；
6. C 提供真实 API 后切换数据源；
7. 准备答辩演示脚本和异常场景。

### 推荐页面内容

- 4#、5# 设备 RUL 数值卡片；
- 预测区间图，而不是只显示单一小时数；
- 退化趋势图；
- RUL、健康分、风险等级的联合视图；
- 调度前后加载率对比；
- 数据来源和验证模式；
- “模型建议，需人工确认”的显著提示。

### D 的演示场景

1. 两台设备健康、RUL 较长，按能效正常调度；
2. 5# 出现加速退化且 RUL 降低，调度智能体降低 5# 负载；
3. RUL 服务异常，系统自动退化到健康分规则，页面提示服务降级；
4. RUL 很低但供气压力不足，系统不盲目停机，而是产生风险告警和人工确认请求。

### D 的验收标准

- fixture 和真实 API 使用同一前端数据模型；
- 切换数据源不需要修改页面字段；
- 上下界、置信度和 `simulation` 标识均可见；
- 页面不把模拟 RUL 描述为真实寿命承诺；
- API 失败时有可理解的降级提示；
- 能完整演示 RUL 影响调度但不越过安全控制边界。

## 9. 第五步：B 接入真实 RUL 软约束

B 把 fixture 调用替换为 C 的 MCP/API 或项目约定的内部服务调用，并完成以下对比：

## 11. 第七步：四人联合测试

## 11.1 正常链路

```text
设备/特征数据
  → A: rul_json()
  → C: rul_estimation MCP / REST
  → 健康智能体读取 RUL
  → B: 调度智能体增加软约束
  → C: 安全与控制工作流校验
  → D: 页面展示结果和解释
```

验收：字段一致、结果可解释、调度可运行、页面显示正确。

## 11.2 低 RUL 场景

- 让 5# 进入加速退化阶段；
- A 输出较低 RUL 和更宽预测区间；
- C 正确传递；
- B 降低 5# 调度优先级；
- D 展示风险、区间和调度变化；
- 系统不绕过安全约束直接停机。

## 11.3 服务失败场景

- 模拟模型文件缺失、接口超时或非法输出；
- C 返回明确错误；
- B 回退到现有健康等级策略；
- D 显示“RUL 服务暂不可用，当前使用健康风险降级策略”；
- 系统核心调度不中断。

## 11.4 极端冲突场景

- 一台设备 RUL 很低；
- 另一台设备能力不足或处于喘振高风险区；
- 系统优先满足硬安全约束；
- 调度智能体输出保守方案；
- 控制智能体不自动执行高风险动作；
- 页面要求人工确认。

## 12. 协作和提交顺序

建议各成员独立分支：

```text
A：feat/a-rul

C：feat/c-backend-agent
```

4. C 合并真实 `rul_json()` 适配；
5. B 合并真实 RUL 软约束；
6. D 合并真实 API 接入；
7. 创建联合集成分支或通过主分支完成端到端测试；
8. 测试通过后冻结演示版本。

任一成员若要修改冻结字段，必须先由 A、B、C、D 共同确认。不要让四个人各自定义一套 RUL JSON。

## 13. 最终完成标准

RUL 增强能力只有同时满足以下条件才算完成：

1. A 能通过独立函数稳定输出 RUL、区间和限制说明；
2. B 能把 RUL 作为软约束影响调度，同时保持供气与安全硬约束；
3. C 能通过 MCP/API 向智能体和前端提供 RUL，并能正确处理失败；
4. D 能展示 RUL、预测区间、调度影响和模型限制；
5. 多智能体能够完成“感知—健康推理—调度决策—安全校验—展示/人工确认”的闭环；
6. 所有报告明确：目前 RUL 基于模拟退化数据，只用于方案验证和辅助决策，不代表真实寿命承诺。
